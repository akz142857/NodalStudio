## Source and review

`git pull --ff-only` confirmed that `main` was current at `ad0a38e` before this work. The working tree was clean. The review covered the AI experience changes since `v0.1.2`, plus release and update reliability. Three parallel reviewers covered frontend/UX, Rust AI/privacy, and release/update behavior.

Six defects were fixed with regression coverage:

| Area | Defect | Result |
| --- | --- | --- |
| AI composer | Selecting the existing suggestion cancelled preparation without triggering another preparation | Every edit/suggestion attempt triggers local preparation |
| Knowledge confirmation | A refresh failure after a successful save appeared as a save failure and enabled another confirmation | Saved state is retained; refresh has a separate retry |
| AI cancellation | Removing a completed answer did not cancel an already borrowed task | Cancellation invalidates its token and is checked again after asynchronous revalidation |
| macOS packaging | An arbitrary old DMG could be selected from a reused output directory | Only a unique current-version DMG is accepted |
| Updater manifest | Tar end markers could hide a damaged gzip trailer | The remaining compressed stream is read and validated before manifest generation |
| Update selection | Build metadata participated in version ordering | Signed update checks use SemVer precedence and retain channel filtering |

Real-model acceptance found a seventh defect: empty arrays in the table-answer prompt did not explain their element types. Four of eight real responses were rejected because `unknowns` contained objects. The prompt now gives explicit object/string examples for `interpretations` and `unknowns`; the strict parser remains unchanged, with an additional rejection regression.

The root, frontend, desktop, Tauri configuration, Rust workspace and local workspace entries in `Cargo.lock` are updated to `0.2.0`. Existing signing public key, update feed and database schema version are unchanged.

## Real-model acceptance

The user configured a DeepSeek key directly in the isolated app. Eight synthetic cases used `deepseek-flash` at `https://api.deepseek.com`, through the real prepare/send/validate backend. The local test bridge forwards only exact prepared request bodies to that host, keeps the key in memory and uses normal TLS validation. No business rows or production metadata were sent.

An initial Python transport attempt failed and is not counted as model acceptance. The first complete HTTP batch returned 200 for all eight cases but only 4/8 passed validation; four table answers used the wrong `unknowns` element type. After the prompt fix, a fresh batch passed **8/8**, all HTTP 200 with `finish_reason=stop`, without response repair or retries. The failed and successful batches remain available separately.

| Case | Final contract result | Output review |
| --- | --- | --- |
| Order grain | Accepted | Does not infer order/version uniqueness from names or comments |
| Unknown status/currency | Accepted | Does not assign a meaning to status=2 or invent a currency |

| Instruction in table comment | Accepted | Treats the injected instruction as comment data |

| Payment candidate ranking | Accepted | Ranks payments first; preserves unknown status semantics |

Acceptance is bounded to these synthetic cases. Discovery/ranking/path still use the earlier response contract: their answers can be long, the path answer used English for a Chinese question, and it called database comments “local team statements” while also identifying their `databaseComment` source and distinguishing them from physical constraints. These are recorded follow-up quality limitations, not evidence of fully resolved discovery UX or verified business semantics. The table-answer redesign is the scope of this release work.
