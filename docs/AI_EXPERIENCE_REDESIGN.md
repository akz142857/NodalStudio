# AI 体验调整：让问题得到解决

日期：2026-10-23。状态：用户已批准实施第一阶段，代码与回归检查已完成，原生实际验收因 Mac 锁屏中断，待换机继续。基线：v0.1.2、用户提供的六张原生界面截图及当前 main 源码。实施与验证、换机交接见 [阶段一验收记录](AI_EXPERIENCE_STAGE1_ACCEPTANCE.md)。

## 1. 结论

右侧 AI 的首要工作是让用户理解当前对象、找到关联对象并继续工作。默认界面应围绕 **一个问题、一段直接回答、一个有用的下一步** 组织。证据随结论可查，发送范围随请求可见，诊断信息进入详情。

现有 F1–F4 的产品方向仍成立：找表、理解表与字段、理清关联、保存确认后的理解。需要重做的是回答结构和操作层级，而不只是缩小字号或折叠几个区块。

首轮优先改好当前表的解释；随后统一业务找表和关系解释的呈现。已有 SQL 草稿入口继续使用现有编辑器，不增加一套执行入口。

## 2. 当前体验为什么难懂

| 当前界面与实现 | 对用户的影响 | 调整方向 |
|---|---|---|
| 提问前依次展示提供方、隐私说明、快照编号、四个大按钮、问题框、字段选择、范围和设置跳转 | 用户先理解工具的配置，才能问业务问题 | 选中对象即绑定上下文；输入框与少量相关建议为主 |
| Prepare request preview → Send this request | 内部准备过程成为用户步骤；主要按钮表达技术动作 | 本地准备自动完成；发送前给可读摘要和一个明确发送动作 |
| 答案位于整套表单下面 | 阅读答案时还要穿过准备请求的界面 | 请求提交后压缩提问表单，答案成为主区域，追问输入保留 |
| 每个解释条目都有 e1/e3 等按钮和 Generate annotation draft | 证据编号没有意义，保存操作与主要结论争夺注意力 | 依据显示对象名称；整份回答只保留一个次要的“整理成表说明”入口 |
| 所有内容都归到 Business interpretations · unverified | 主键等可验证结构事实也被表达成推测，可信信息层级混乱 | 事实由程序从快照提供；业务解释逐项保留依据与限定语 |
| 八条左右的待确认问题 | 用户得到更多待办，却不知道哪个影响当前判断 | 默认只呈现会改变当前答案或阻断下一步的缺口 |
| 成功后仍展示请求地址、有效期、JSON、完整证据账本 | 诊断信息挤占任务空间 | 请求详情通过次级入口查看；成功后的有效期不再作为待办 |
| 中文回答、英文操作、内部枚举混用 | 每一步都需要额外理解 | 操作文案跟随应用语言；表名、字段名保持原样 |

更深层的原因在返回契约：`ModelUnderstanding` 只有 `interpretations[]` 和 `unknowns[]`；系统提示最多允许各 12 项、每项 2000 字符，并要求不返回 facts 或 actions。这是容量上限，不代表模型必须写满，但契约没有“先回答问题”的位置。前端随后逐项渲染，逐项附上证据与保存按钮。

另一个问题是“看不到”和“不知道”被混在一起。当前表范围可能排除跨表关系，模型因此提出“customer_id 是否关联其他表”；本地完整快照可能已有确定外键。应用应该先用本地能力回答可确定的部分，需要远程解释时再申请所需范围。

## 3. Claude、Apple、OpenAI 提供什么启发

以下“应用到 Nodal Studio”是基于公开资料的设计推演，不代表三家针对本产品的意见，也不把各家的共同原则说成独有能力。

| 参考 | 可核实的公开设计方向 | 应用到 Nodal Studio 的推演 |
|---|---|---|
| Claude | Artifacts 与对话并列，可直接编辑、继续迭代并再次使用 | 用对话澄清问题，把可用成果放回工作区：关联路径进入画布，确认后的表说明进入语义层；短问题不生成一份长报告 |
| Apple | AI 应在具体场景提供明确价值；用户能调整、重试或撤回结果；明确传输内容，尽可能本地处理 | 用户选中字段即可“解释此字段”；已知结构就地呈现；默认控件少，保存时查看改动，保留可取消、可恢复的过程 |
| OpenAI | UI 补充对话，避免重复内容；轻量单一任务卡片；一个主操作与至多一个次操作，避免嵌套滚动 | 提问后返回一张紧凑任务结果；按钮应能“定位关联”“查看字段”或“放入查询编辑器”，而不是要求用户再次解释接下来要做什么 |

来源（2026-10-23 查阅）：[Claude Artifacts](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them)、[Apple Generative AI HIG](https://developer.apple.com/design/human-interface-guidelines/generative-ai)、[OpenAI UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines)。OpenAI 的控件数量规则来自 ChatGPT 内嵌 UI，不是对所有桌面界面的硬性规定；这里借用其减少竞争操作的原则。

推荐取三者的共同方向：贴近正在进行的工作，让用户能继续操作，让必要的依据和控制随时可达。

## 4. 用户任务决定结果形态

| 用户的问题 | 默认结果 | 首要操作 | 完成的标志 |
|---|---|---|---|
| “这一行代表什么？” | 1–2 句记录粒度解释，附影响判断的一项限定 | 查看关键字段；无必要时不强塞按钮 | 用户能说清可能的记录单位和不确定边界 |
| “订单和客户怎么关联？” | 已有外键的字段映射与方向；必要时补充业务解释 | 在画布定位关系 | 能指出连接字段；不把结构引用等同于业务流程 |
| “status = 2 是什么？” | 如已有字典则引用；否则明确当前资料缺少映射 | 在已有团队说明中核对，或补充说明 | 不猜测 2 是“已支付”，用户知道缺什么 |
| “支付失败在哪看？” | 少量候选表、每项一行匹配理由 | 打开最相关的表或局部图 | 找到可继续阅读的对象；无结果时明确说明 |
| “帮我查重复订单号” | 跳转现有 SQL 草稿工作流，澄清重复口径 | 在查询编辑器审阅 | 得到可审阅草稿；生成不等于执行或验证数据 |
| “把刚才的理解记下来” | 一个可编辑的对象说明草稿、目标、原说明和改动 | 确认保存 | 保存到语义层，保留依据和原有不确定性 |

关联字段、主键、唯一约束、已知图路径可由本地程序确定；大模型主要负责业务语言理解、解释和必要的歧义澄清。不要为了展示 AI 而调用模型复述全部字段。

## 5. 右侧面板的推荐结构

### 默认状态

1. 当前对象名称与“AI 助手”。表名已经在 Inspector 标题中时，不重复两次。
2. 一个问题输入框，提示“想了解这张表的什么？”；最多 2–3 个与当前对象有关的短建议。选中字段时自动携带字段，不常驻“Whole table”选择器。
3. 紧凑范围行，例如“DeepSeek · 当前表 · 含注释”，可查看将发送的内容。提供方未配置时才显示设置入口。
4. 一个清晰的发送操作。发送正文与范围摘要不需要分散到几个屏幕。

### 回答状态

- 用户问题压缩为一行；答案从面板主要区域开始，输入框用于继续提问。
- 简单问题先给 1–2 句直接答案；默认约 80–180 个中文字，属于设计目标，不是截断规则。复杂任务可展开，也可使用图和结构化结果。
- 只展示影响当前判断的补充事实或缺口，默认最多 3 个要点。与当前问题无关的币种、时间戳、生成机制不主动列入。
- 依据显示为“id 主键”“order_number 注释”等可理解的名字，点击能查看来源并定位对象。内部 e-ID 仅供诊断。
- 按任务提供 0–1 个主要下一步；“整理成表说明”放在次要位置。既不每句话保存，也不默认把整段回答写入数据库说明。
- 请求 JSON、模型版本、耗时、快照指纹和审计信息进入“请求详情”；不因视觉简化删除它们。

推荐示例，限于已提供的合成 orders 元数据：

> **它很可能是一条订单主记录。**
>
> 表与字段注释支持这个理解；结构上 `id` 唯一标识每行。当前资料不能确认同一订单是否会保存多个版本。
>
> 依据：表注释 · id 主键
>
> 查看关键字段　　整理成表说明

这里仍保留“很可能”和版本粒度的限制，不把短答案变成过度肯定。状态码和币种的未知留到用户问相关问题时再说明。

### 追问与工作区联动

追问需明确绑定来源、快照、表和字段。切换对象时开始新上下文；旧结果可以返回查看，但标明原对象，不自动带入另一张表或跨来源发送。

关系问题优先打开已有局部图，当前选择和布局可返回。单纯在本地查看关系不扩大远程发送范围。只有用户要求 AI 进一步解释时，才准备需要的对象集合。

不新增几个互相独立的 AI 面板。单表解释、业务找表、关联解释在视觉和请求反馈上统一；底层保留各自已验证的能力与权限边界。现有业务找表入口先保留，跨入口的任务连续性作为第二阶段改动。

## 6. 减少操作，同时保留发送控制

先区分“产品手动点击两次”和“后端必须先准备再运行”。后端 prepare/run、实际请求体、对象白名单、有效期和配置签名继续保留。

**第一阶段，保持逐次发送确认语义：**

- 用户编辑问题后，应用自动在本地准备，不调用模型。准备期间显示简短状态。
- 准备完成显示“将向 DeepSeek 发送 orders 的结构、允许的注释和你的问题”，按钮为“发送并回答”。JSON 可按需打开；仅输入或点选问题建议不会外发。
- 问题、对象、范围、提供方或设置变化时，准备结果失效并重新生成；旧请求不能继续使用。

**第二阶段，可选的持续授权体验：**

- 如决定支持同一已授权范围内的一步提问，必须新增明确的授权契约与有效性校验；不能只在前端把 prepare 和 run 串起来。
- 用户主动选择“本来源、此提供方、此范围内直接发送”后，普通提问可一步提交。始终可查看实际内容、取消后续调用和撤销此偏好。
- 扩大对象集合、切换提供方、增加注释/团队说明种类，重新展示变更摘要。组织策略仍为上限，局部选择不能绕过。
- “本次增加关联表”应是独立请求范围，不暗改长期设置；若当前策略不允许，则解释原因并保留本地查看关系的能力。

元数据与用户输入也可能敏感。页面缩短不能暗示它们天然安全；范围摘要要准确说明允许的注释与本机已确认团队说明是否包含。默认不采样或上传业务行，也不发送连接凭据。

## 7. 回答契约与质量必须一起调整

建议增加版本化的展示契约，而不是从现有长列表直接取前三项：

| 部分 | 职责 |
|---|---|
| 主答案 | 直接回应这一次问题；必要的限定语和有效引用必须附着在答案本身 |
| 相关补充 | 少量与问题有关的解释，每条保留引用；不重复事实清单 |
| 关键缺口 | 说明具体缺失的信息如何影响当前答案；没有缺口就为空 |
| 可核查事实 | 由应用从白名单快照或有效团队说明生成，清楚区分约束、注释、团队说明 |
| 后续操作 | 由应用根据意图、有效对象引用和当前能力提供固定操作；模型不能生成任意命令或取得执行权 |

所有业务解释仍是未独立确认的推测，不能靠模型自己输出 `fact=true` 提升可信级别。引用存在只能证明模型指向了某项材料，不能证明该材料支持结论；验收要检查证据与结论是否相符。

“整理成表说明”需要明确支持选择或合并多个相关论点，生成一份独立草稿。当前 `interpretationIndex` 单条接口不能不经设计就变成整段保存。保存前保留目标、原文、编辑、冲突校验和不确定性；程序事实无需重复保存为业务说明。确认是用户接受团队说明，不会改变物理约束或把推测变成数据库事实。

现有 v0.1.2 发布后真实模型合成复测曾出现 `evidenceIds` 返回字符串、被严格校验拒绝的问题，详见 [v0.1.2 验证记录](releases/v0.1.2-validation.md)。体验改版应覆盖格式失败的恢复，不靠截取自然语言或静默放宽引用校验掩盖失败。

## 8. 状态与异常

| 状态 | 面向用户的表现 |
|---|---|
| 未启用 / 未配置 | 一句话说明与“配置 AI”；已知结构仍能本地查看 |
| 本地准备 | “正在整理当前表的结构”；可继续编辑，无外发 |
| 远程等待 | “正在解释 orders”；提供取消；长耗时显示实际状态，不伪造进度 |
| 结构不足 | 展示已有结论及具体缺口；提供有意义的补充入口 |
| 无外键或路径 | 说明当前快照未找到已知关系；名称相似的候选另作标记 |
| 范围不足 | 说明本次模型未获得哪些必要对象；可本地查看或明确授权本次扩展 |
| 超时 / 断网 / 凭据失败 | 保留问题和当前视图，给对应恢复动作；详细错误可展开 |
| 格式失败 | “回答未通过校验，请重试”；不把未校验片段呈现为完成答案 |
| 输出截断 | “回答未完成，请重试或缩小问题”；不保存部分结果，不展示思考内容替代答案 |
| 切换对象 / 快照 / 策略 | 隔离晚到响应；旧结果标明来源且不能保存到新目标 |
| 保存失败 / 冲突 | 保留草稿，显示冲突和重新核对入口，不静默覆盖 |

输入、结果、引用和按钮须可键盘访问；大字号不裁切结论；窄面板只保留一个主要滚动区域。取消远程请求只能阻止后续处理，不能宣称撤回已经发送的数据。

## 9. 实施次序与验收

**阶段一：把单表问答做完整。** 重排 `TableAiAssistant`，自动本地准备加单次发送，答案优先、依据按需、请求详情收起、简化保存入口、统一语言。同时修改版本化回答契约与提示，不按索引裁掉关键限定。复用现有设计系统，不引入新的一套样式。

**阶段二：把回答接回实际工作。** 本地确定性事实优先；关系定位与明确的本次范围扩展；跨单表/找表/路径的任务连续性。持续授权如有必要再加入，不作为第一阶段的前提。SQL 继续复用现有草稿、审阅和执行边界。

**阶段三：按真实使用结果调优。** 小范围任务测试、观察误解点，再调整默认摘要长度与建议。不要先扩成全库问答、自动分析代理或一键生成整库文档。

验收分为三层，不能互相替代：

1. **交互验收：** 首次回答在约 420 × 700 CSS 像素可用面板中看到结论、关键限定和下一步，无需滚过配置；正文不靠缩小字号达成。普通发送在准备完成后只需一个提交操作。依据和保存入口按需展开，键盘与大字号可用。
2. **任务效果：** 用户能回答“这张表的一行可能是什么”“通过哪个字段关联”“状态码为什么还不能确定”；关键字段/关联可一次操作定位。不主动堆砌无关未知。复杂问题不为了字数目标丢失必要内容。目标需通过用户任务测试验证，目前未实测。
3. **工程与模型验收：** 原有 8 项合成测试继续保留，记录每个真实模型批次的原始成功率与失败；新增任务相关性、证据支持度、事实/推测区分、动作定位和关键限定检查。覆盖输出截断、错误 JSON、晚到响应、设置变动、范围边界、注解冲突。前端模拟通过不等于原生端或真实模型通过。

对比基线应记录：达到正确理解所需时间、点击/滚动次数、定位是否成功、是否把推测当成事实、是否知道请求发送了什么。测试通过数与回答字数只能作为辅助指标。
