# Mac App Store 购买授权与免费／付费版本实施方案

日期：2026-10-25。状态：**待产品评审，仅方案，尚未实施**。

本文不授权修改许可证、仓库可见性、已有发布资产或功能权限；不提交、不发布。用户确认商业边界后，再开展开发。

## 1. 建议与目标

建议采用「GitHub Community 免费版 + Mac App Store 买断 Pro」，公共基础能力继续开放，未来新增的商业工作流模块在完成权属核查后单独闭源。首期不做独立账号、许可证服务器、订阅、设备席位管理或跨平台购买互通。

付费价值应是：**数据库变化后，团队已有的理解能够持续复核、复用并交付。** 不以 SQL 编辑器右键菜单、基本 ER 图、单纯 AI 聊天、限制用户取回数据作为购买理由，也不引入修改数据库表结构的定位。

这是一项建议，不是已经确定的版本划分。如果短期没有足够的 Pro 差异，先保留现有免费产品；不要把相同功能包装成“必须购买才能使用”。

授权目标是阻止普通用户将商店版应用和本地授权文件直接复制到另一台未获授权的 Mac 后使用 Pro。不能承诺抵御二进制破解、系统攻破、源码修改重编译或所有账号共享。

## 3. 免费下载、开源、付费是三个决定

| 方案 | 用户为何付费 | 主要代价 | 本方案意见 |
| --- | --- | --- | --- |
| GitHub 与商店功能完全相同，均提供完整源码 | 商店安装更新方便、支持作者 | 免费替代品完整存在，购买校验不能改变这一点 | 可以做支持版，但不适合作为主要功能付费模式 |
| Community 免费 + Pro 商业模块 | 持续复核、交付与团队工作流节省时间 | 需维护清晰能力边界、构建和授权 | 推荐作为下一阶段方向 |
| 后续版本全面闭源、商店付费 | 新版本整体价值 | 获客和信任成本更高；仍需处理历史授权和免费旧版 | 可选，不建议仅因担心复制就立即执行 |

公开源码不必然代表具有完整开源许可；免费安装包也可以不开源。另一方面，MIT 许可允许使用、修改和再分发：若继续公开完整 Pro 实现并对其授予 MIT，就不能指望本地购买开关阻止别人合法制作另一个版本。出处：[GitHub 许可证说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)、[MIT 条款](https://choosealicense.com/licenses/mit/)。

关闭仓库不会收回已经分发出去的代码和安装包，也不能简单追溯撤回已授予的许可。未来代码如何授权，要核查作者权属、外部贡献、依赖许可和历史发布声明；保留适用的版权及许可通知。本次不直接改 MIT 元数据，也不删除旧版本。

### 3.1 推荐的能力边界（提案）

| 用户任务 | Community | Pro 增量方向 |
| --- | --- | --- |
| 认识数据库 | 连接、结构浏览、基础图形、已有 DDL 导入与预检能力 | 不把基本理解能力设为主要付费门槛 |

| 完成复核 | 保留已发布能力；本地 P0 的归属需单独确认 | 将批量处理、归档恢复与跨轮次流程组合为完整效率价值，而非只售一个按钮 |

| 数据可携带 | 始终允许取回自己的笔记、结构与已有记录 | 不以授权失效阻断基本备份和数据导出 |

上述 Pro 项目是产品方向，不表示已经全部实现。开发前要逐项对照 v0.2.4、公开 main 和本地未发布改动，形成「已公开／已发布／仅本地／尚未开发」清单。不能把公开过的实现误认为仍是独有商业资产。

建议先确定一个能演示的付费闭环：“结构变化 → 已有解释受影响 → 复核 → 确认可靠基线 → 导出带依据的交付包”。在这个闭环成立前，不急于大范围拆分仓库。

### 3.2 售卖形态

本文技术主线按 **付费下载的 MAS Pro** 设计：商店完成付款，应用验证 AppTransaction。不要再让已经付费下载的用户购买第二次解锁。

备选是「MAS 免费下载 + 非消耗型 Pro 内购」。这种情况下 AppTransaction 只能证明获取过免费应用，**不能证明购买 Pro**；必须另做 Transaction.currentEntitlements、指定 product ID、交易更新与恢复购买。不能把两种方案混用。若选择该备选，需先修订本文授权模型再开发。

首期买断指所购产品的本地能力无周期到期，不承诺无限 AI 云成本或未来所有独立产品免费。AI 若继续使用用户自己的服务配置，要明确其费用不包含在应用买断价内。

## 4. Apple 约束与可信边界

Apple 的 MAS 规则要求沙盒运行、通过商店更新，并限制启动许可证屏幕、许可证密钥及自行实现的复制保护。因此本方案使用 Apple 购买凭据与官方设备验证，不做序列号、MAC 地址绑定、硬件指纹、自建激活页面或私有授权协议。参见 [App Review Guidelines 2.4.5](https://developer.apple.com/app-store/review/guidelines/)。

首选原生 StoreKit `AppTransaction.shared`，只接受 `.verified` 结果，再核对预期应用身份及允许的运行环境。Apple 推荐现代 AppTransaction 用于应用购买验证；传统 receipt 路线只在现代 API 无法满足兼容性或已验证的离线场景时评估。参见 [验证方式选择](https://developer.apple.com/documentation/storekit/choosing-a-receipt-validation-technique)。

本地保护的边界：

- React 只显示状态，不能凭 localStorage、页面参数、请求字段或 `isPro=true` 获得权限。
- Rust 原生服务是所有 Pro 命令的权限入口；Swift 负责与 StoreKit 交互并返回结构化结果。
- 购买凭据不混入项目数据库、Git 导出、交付包或普通偏好设置；拷贝工作区不能带走授权。
- 不向自建服务上传购买记录、Apple 账号、数据库结构、SQL 或连接密码；本方案没有自建服务。
- Apple 账号、合法的多设备使用与适用的家庭共享由 Apple 机制处理，不另造“一人一机”规则。

## 5. 授权流程与离线策略

### 5.1 启动与日常使用

1. 原生读取编译期渠道与版本身份，Community 直接使用免费能力集合。
2. MAS Pro 正常打开工作区，同时异步读取 StoreKit 信息；不弹自定义启动激活墙，不阻塞查看已有数据。
3. 收到 `.verified` 后校验 bundle ID；适用时核对 App Store app ID，按正式／测试构建接受对应环境，并验证官方设备关联。
4. 验证通过后由 Rust 发布能力快照，解锁 Pro；工作区不需要刷新或丢失选择。
5. 无有效凭据时不推断用户盗版。显示“暂时无法确认 App Store 购买”，保留基本查看与数据取回能力，提供明确恢复入口。

Apple 官方设备验证是将 nonce 的小写 UUID 字符串与 `AppStore.deviceVerificationID` 的小写 UUID 字符串按顺序拼接，计算 SHA-384，与 `deviceVerification` 比较。设备标识不可用或不匹配时不能授权；不得用应用自己生成的 UUID 替代。参见 [Apple 设备验证说明](https://developer.apple.com/documentation/storekit/appstore/deviceverificationid)。实现时同时核实 StoreKit `.verified` 已提供的设备验证保证，避免以自创规则替代平台校验。

### 5.2 离线使用承诺

目标：在该 Mac 完成过有效购买验证、Apple 本地凭据仍有效的情况下，断网启动、重启应用和重启系统均可使用 Pro；不设置 7／30 天联网续期，不把普通网络失败视为购买失效。

必须区分“无网络”和“无有效凭据”。Apple 明确说明获取 AppTransaction 可能需要联网或 App Store 认证，因此不能仅凭调用了 shared 就宣布离线场景已解决。参见 [AppTransaction.shared](https://developer.apple.com/documentation/storekit/apptransaction/shared)。

实施路线：

1. 先用真实签名测试包验证 StoreKit 在已授权设备上跨进程、跨系统重启的离线行为。
2. 优先使用 StoreKit 管理的本地已验证凭据，不自制一个永久 `activated=true` 标志。
3. 如果 shared 在目标系统的离线场景不能满足目标，则在开发评审中选择 Apple receipt 的本地签名／应用身份／设备关联验证作为离线补充；补充验证模块和负面测试通过前，不能宣布支持该场景。不能将未经签名验证的 JWS 解析结果或过去的成功布尔值当作替代。
4. 持久化缓存只保存界面展示与诊断元数据；它本身没有授权效力。需要缓存签名材料时，须把完整本地验证方案单独补齐，不能因放进 Keychain 就认为可信。
5. 新设备、系统凭据被清除、重装后无法取得有效材料时，需要联网由 Apple 恢复；保留用户数据并解释原因。

**开发首个里程碑必须验证这条离线路径。** 不把这一技术不确定性留到发布前；若现代 API 与本地 receipt 路线均未通过实机测试，暂停发布并修订承诺。

纯离线无法实时获知退款或 Apple 侧后续撤销，这是本方案接受的边界。网络恢复后遵循 Apple 返回的最新有效结果；不能把查询超时、用户取消登录或未知错误等同于退款。付费应用与 IAP 的退款／撤销接口并不相同，禁止直接套用 IAP 的 revocationDate 到 AppTransaction。

### 5.3 恢复购买与异常交互

设置增加「版本与购买」区域：渠道、Community／Pro、授权状态，以及“重新验证 App Store 购买”和“在 App Store 查看”。正常用户无须手动操作。

- 主动点击重新验证：调用 `AppTransaction.refresh()`，允许 Apple 系统认证界面出现；完成后重新评估。
- 不在每次启动、轮询或失败重试中自动调用 refresh；它可能要求登录，只能由用户显式触发。参见 [AppTransaction.refresh](https://developer.apple.com/documentation/storekit/apptransaction/4020517-refresh?changes=_5_5)。
- 离线但已有有效本地凭据：显示“Pro · 可离线使用”，不显示倒计时。
- 无有效本地凭据：提示联网重新验证，不弹出第二次付款要求；不展示许可证输入框。
- 用户取消认证：回到原页面，不重试轰炸；既有有效凭据不因取消而失效。
- 检测到可信的不匹配／无效证据：阻止新 Pro 操作，仍允许查看和基本数据导出，不删除或自动归档工作内容。
- 换 Mac：从 App Store 使用有资格的 Apple 账号重新下载并获取新设备凭据；不导入旧机器的“授权文件”。

## 6. 技术结构与数据模型

建议新增下列模块，路径是实施提案：

| 层 | 模块 | 责任 |
| --- | --- | --- |
| 原生 Swift | `apps/desktop/src-tauri/native/storekit/` | StoreKit 异步请求、官方验证结果、取消与错误归类 |
| Rust | `src/purchase/provider.rs` | 统一 provider 接口，隔离平台实现；测试使用 fake provider |
| Rust | `src/purchase/state.rs` | 状态机、请求代次、能力快照、并发去重 |
| Rust | `src/purchase/policy.rs` | 版本与能力映射、所有 Pro command 的服务端检查 |
| React | 设置中的版本与购买面板 | 显示状态与恢复操作；不持有授权真相 |
| 构建 | Cargo features、build.rs、商店配置与脚本 | 编译渠道隔离、Swift 链接、架构与系统版本验证 |

Swift 以进程内 C ABI 回调桥接 Rust，明确字符串分配／释放和 callback 生命周期；不启动外部 helper、不把 receipt 作为命令行参数。不在主线程同步等待网络；应用退出／请求取消后不能调用已释放对象。原型阶段确认 Swift runtime 链接和 Universal 构建打包。

建议 MAS 首版以 macOS 13+ 为兼容基线候选，开发前通过目标 SDK 的 availability 和真实测试确认；若需要更低系统，重新评估 receipt 路线。不得顺带提高 Community 的系统要求。

```text
Distribution = Community | MacAppStore
Edition = Community | Pro
PurchaseState = Checking | Verified | NeedsRecovery | Unverified | Unsupported
ProofSource = StoreKit | AppleLocalReceipt

PurchaseSnapshot {
  distribution, edition, state,
  capabilities[], reasonCode?, checkedAt?, proofSource?
}

NativeVerifiedEvidence { // 仅原生进程可构造，不接受前端反序列化
  expectedBundleMatched,
  environment,
  deviceVerified,
  proofSource
}
```

`checkedAt` 仅用于展示／诊断，不是过期时间。前端不接收原始 JWS、receipt、设备标识或完整交易标识。Pro 权限由“构建所含能力 ∩ 原生验证允许能力”计算，不能由保存的 edition 字段决定。

状态机规则：

- Checking → Verified：仅可信 provider 验证成功。
- Checking → NeedsRecovery：没有可验证材料、需联网或需认证；不直接标记为未购买。
- 任意状态 → Unverified：发现可信材料校验失败；禁止从该材料解锁。
- Verified 遇到 refresh 超时／取消：保留仍有效的既有证据；不能误降级，也不能覆盖成永久缓存。
- 新结果替代旧结果必须按请求代次处理，过时的成功回调不能覆盖更新的无效结果。
- 并发恢复请求合并；能力变化通过单一原生事件传播，不使组件各自维护相互冲突的 isPro。

每个 Pro 命令在执行前由 Rust 检查能力；批处理、快捷键、菜单、直接 invoke 和导出路径共用检查。已经开始的本地原子事务按事务完成，不在中途制造半完成数据；后续新操作使用最新能力快照。授权信息不写入现有业务表，不影响 P0 分页、已阅与归档事务。

## 7. 分发与数据兼容

- 明确编译期 `community`／`mas` 渠道；正式构建禁止测试授权 provider、环境变量解锁和开发开关。
- Community 不打包闭源 Pro 模块。隐藏按钮或前端布尔判断不能替代模块与权限边界。
- MAS 构建移除 GitHub updater 插件注册、相关命令与设置入口，并清理继承的 feed；商店更新不能落回 GitHub 手动更新路径。
- Community 保留原有更新通道。测试验证两个渠道不会交叉安装或错误覆盖。
- 若 Pro 代码采用闭源授权，必须在提交公共仓库之前完成模块和源码分发边界；不得先公开再把权限开关当成保密措施。
- 新 MAS 身份、App Store app ID 与 provisioning profile 必须一致。现有 bundle ID 已用于站外版，是否复用或使用独立 Pro ID 需在创建商店产品前确定；倾向独立身份便于并存，但本方案不直接改 ID。
- MAS 沙盒数据目录与站外版可能不同，使用用户主动选择文件的导入／导出流程迁移；复制业务数据不复制购买凭据。
- 不自动搬运 Keychain 密钥，不覆盖旧工作区；需要时由用户在新渠道重新配置凭据。迁移前后校验连接元数据、笔记、历史和复核状态，支持回退。
- 无独立账号服务时，MAS 购买不会自动解锁 Windows 或站外 Pro；首期文案明确 Mac App Store 版范围。

| 3：界面流程 | 版本面板、恢复购买、错误与离线提示 | 无启动激活墙、无重复购买提示、取消与网络错误可恢复 |
| 4：分发隔离 | MAS updater 清理、编译渠道、Universal 与沙盒适配 | 正式包无测试后门；Community 更新流程未退化 |
| 5：数据与验收 | 并存、导入／导出、实际商店环境验证 | 数据保持、原生测试矩阵和未通过项报告 |
| 6：发布评审 | 定价、商店文案、审核材料与所有阻断项 | 另行获得发布指令；测试通过不自动发布 |

不在本轮实现 Pro 新业务功能。购买基础设施完成也不代表产品已经有足够付费价值；商业闭环验收与授权验收分别进行。

## 9. 测试与验收标准

### 9.1 自动化

| 场景 | 必须满足 |
| --- | --- |
| 已验证／缺失／损坏／身份不匹配凭据 | 只有有效且匹配的证据获得 Pro |
| 前端改状态、改本地数据库、伪造 invoke 参数 | 无法绕过原生能力检查 |
| 复制 UI 缓存、设置、工作区或旧授权材料 | 不能为新设备建立授权 |
| 离线、认证取消、超时 | 与“明确校验失败”分开处理，不误删数据、不循环弹窗 |
| 并发请求、迟到回调、关闭应用 | 状态不倒退、无重复刷新、无悬空回调 |
| 系统时间变化 | 不因自建试用计时误降级；不能用时间回拨生成授权 |
| Pro 批量操作过程中状态变化 | 事务一致，既有数据不出现部分写入 |
| Community／MAS／测试构建 | 正式包不含测试 provider，MAS 不暴露站外更新入口 |
| 旧数据迁移与回退 | 连接元数据、笔记、历史、复核记录保持；不迁移购买授权 |

### 9.2 原生实机矩阵

| 操作 | 验收结果 |
| --- | --- |
| Mac A 通过 Apple 正常购买／下载 | 不注册 NodalStudio 账号，自动进入 Pro |
| Mac A 验证后断网，重开应用、重启 Mac | 完整 Pro 本地能力可用，没有联网宽限倒计时 |
| Mac A 在较长断网期间反复启动 | 不因应用自己设置的期限失效；报告记录实际测试时长，不把短期测试夸大为永久证明 |
| 将 .app 拷贝到无购买资格的 Mac B，先断网后联网 | 均不能仅靠拷贝获得 Pro；联网时不能接受 A 的旧设备材料 |
| 同时复制 A 的应用与业务数据／可复制缓存到 B | 数据可查看，Pro 授权不可继承 |
| 有资格用户在另一台 Mac 从商店下载 | Apple 正常授权，不被“一机限制”误伤 |
| 用户取消恢复、网络中断、系统认证失败 | 可回到工作区，已有数据完整，提示可操作 |
| 清除凭据／重装后离线 | 明确提示需联网恢复，不伪装成已验证；业务数据不被清除 |
| 正常应用升级 | 购买不要求重买，数据保持；MAS 更新全部通过 Apple |
| 与 Community 并存并导入数据 | 渠道和数据路径清楚，授权不串用，旧版可回退 |
| 适用家庭共享与退款场景 | 按 Apple 实际资格处理；离线撤销延迟明确记录 |

证据分层：fake provider 证明状态机；Xcode／Sandbox 证明集成；TestFlight 证明相应测试分发；实际商店包证明正式购买与更新。不得把前两层报告成正式购买验收。测试环境准入必须与实际签名分发一致，不能用“所有 Sandbox 一律失败”导致合法 TestFlight 无法测试，也不能让正式生产接受任意伪造测试凭据。

最终放行条件：购买、离线重启、跨设备拷贝阻断、正常换机、恢复购买、数据保持及 MAS 更新隔离均有实际证据；未验收的环境明确列为未通过。没有第二台 Mac 或真实购买条件时，报告缺项，不通过修改测试开关模拟通过。

## 10. 需要用户确认的决策

1. 是否接受推荐的「Community 免费 + MAS 买断 Pro」，而不是同功能支持版或立即全面闭源？
2. 哪些未来工作流构成 Pro 首发闭环？本地 P0 是否进入 Pro，需结合公开范围核查后决定。
3. 是否接受首期只覆盖 Mac App Store 购买，不承诺 Windows／站外授权互通？
4. 是否接受“有有效本地凭据可长期离线；新设备或凭据丢失需联网恢复；不承诺实时离线退款撤销”的边界？

确认上述方向后，先开展许可与能力清单核查、StoreKit 离线／拷贝原型，再进入业务权限接入。本文不代表已具备上架条件。
