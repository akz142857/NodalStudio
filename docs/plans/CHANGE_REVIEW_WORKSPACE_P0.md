# 本轮变化复核工作区：P0 产品与技术实施方案

日期：2026-10-24（Asia/Singapore）  
状态：原始实施方案。当前核心闭环已实现；实际落点、取舍与验证证据见 [P0 实施与验收记录](../CHANGE_REVIEW_P0_ACCEPTANCE.md)。分页、批量已阅和归档恢复的后续实现见 [P0 补齐验收](../CHANGE_REVIEW_P0_EXTENSION_ACCEPTANCE.md)。下文未逐条兑现的设计目标不能视为已验收。

## 1. 定位与交付目标

NodalStudio 帮助开发者理解和核对 AI 构建的数据库。数据库结构由外部工具改变；本功能只读采集元数据，在本地编辑理解、记录判断，不执行结构编辑或迁移。

核心承诺：数据库变化后，保留已有理解，指出哪些依据发生变化，让用户完成复核。不能承诺结构不变就意味着业务语义正确，也不能从快照推断变更来自 AI 或解释修改动机。

首发闭环：已有模型与说明 → 外部修改数据库 → 刷新 → 查看本轮结构变化及理解影响 → 保留/修订/暂缓/归档 → 完成本轮复核 → 显式推进基线。

成功标准：用户无需阅读 JSON，即可回答“发生了什么、影响哪些已保存理解、我还需要处理什么”。

## 2. 当前基础与复用边界

| 源码 | 已有基础 | 实施决定 |
|---|---|---|
| `crates/schema-diff/src/lib.rs` | 快照差异、列改名推断、结构风险 | 复用；改名仍为推断，不自动迁移知识 |
| `crates/semantic-model/src/knowledge.rs` | 确认记录、表/关系/说明依赖、摘要 | P0 保留保守的表级失效规则，不暗中缩小依据范围 |

| `crates/semantic-model/src/lib.rs` | 孤立说明保留、业务域、保存视图 | 增加影响投影，不破坏原始对象引用 |
| `crates/snapshot-store/src/lib.rs` | 采集保存、历史裁剪、来源清理 | 增加工作区脏标记、快照保留与清理规则 |
| `apps/desktop/src-tauri/src/knowledge.rs` | 显式且过期的草稿预览 | 复用准备/提交概念，补齐重启与轮次并发约束 |
| `apps/frontend/src/components/KnowledgeReview.tsx` | 本地待复核列表、确认入口 | 保留单对象入口，并导向统一工作区 |
| `HistoryPanel.tsx` / `SchemaChangesPanel.tsx` | 历史比较和属性对比 | 复用明细组件；任意历史比较与正式复核分开 |

重要现状：说明有效性不只是比较全库指纹，已有表/关系/说明依赖；但表摘要变化可能让与具体改动无关的说明也待复核。P0 明示“所依赖表变化，需人工判断”，不声称已精确判定语义冲突。

## 3. P0 范围

### 必须交付

- 每个本机数据源独立的复核基线和至多一个活动轮次。
- 基线到最新采集目标的结构变化；未处理事项持久保存。
- 说明、逻辑关系、业务域及保存视图的统一影响清单。
- 前后结构、原说明、依赖路径和可理解的提醒原因。
- 显式操作、暂缓理由、处理日志、重启恢复、并发保护。
- 完成本轮前校验，完成后推进基线。
- 数据源身份、采集范围与历史证据缺失的诚实提示。

### 不纳入 P0

- 表结构编辑、DDL 执行、迁移生成与执行。
- 字段/属性级知识依赖改造；先保留表级保守校验。
- 自动改名映射、拆表合表知识迁移。
- AI 自动解释与自动修订、后台外发数据、托管 AI。
- Git 提交归因、ORM 索引、团队审批、跨设备确认共享。
- 完整说明版本浏览、导出复核证明、3D 图与渲染器重写。

P0 的处理日志保留本次前后文本和证据，为未来版本历史提供基础，不将其包装为完整知识版本系统。

## 4. 界面与交互

### 4.1 导航与进入

在现有“变化”工作区加入两个子视图：“本轮复核”（默认）和“历史比较”。不新增与变化页平行且重复的顶层入口。

- 刷新成功后显示非阻塞提示：“检测到结构变化，N 项理解需要复核”，点击进入。
- 主入口角标显示未处理影响项数；结构差异数量单独显示，不混为一谈。
- 无变化时不弹出复核工作区；原有待办仍保留。
- 单表检查面板提供“查看相关复核事项”，带对象筛选进入。
- 历史比较继续允许任意两份快照，但不能在历史预览里确认当前知识或推进基线。
- Web 分享、临时 DDL 来源无写入复核入口；说明“请在桌面已连接来源中复核”。

│ 待处理优先列表 │ [保留并确认] [修订] [暂缓]      │

宽屏左侧列表约 280px、其余为详情；内容宽度不足 800px 时切换列表/详情单栏，通过返回按钮恢复筛选、滚动和焦点。详情较宽时前后并排，窄屏上下排列。具体阈值按现有壳层实测调整。

- 图按需打开为局部上下文；默认聚焦目标和相关依赖，不自动展开全库图。
- 待复核使用琥珀色，对象不可映射显示明确状态文字，新增/移除同时有符号与文本。
- 旧对象可在 before 快照定位；无法在最新图定位时提供历史对象卡片。
- 错误就地展示；保存成功后加载失败显示“已保存，重试加载”，不鼓励重复确认。
- Tab/方向导航、可见焦点、状态播报、减弱动效、中文/英文和 125% 字体均验收。

### 4.3 首次使用

区分“建立比较起点”与“已复核基线”。迁移旧数据时不自动认证用户已有说明。

1. 尚未采集：引导只读刷新。
2. 有快照但无基线：展示“以当前快照建立比较起点”；明确不代表已确认业务含义。
3. 若有旧的待复核或不可映射说明，作为“已有未处理理解”进入初始化轮次；保留原因，不冒充本轮结构变化产生。
4. 已有本机有效确认可以继续有效，不要求全部重复确认。
5. 没有旧说明且无差异时，起点可以直接建立；不创建空待办或伪造一次知识确认。

### 4.4 事项动作

| 对象/情况 | 可用操作 | 效果 |
|---|---|---|
| 对象存在的说明 | 保留原文并确认、修订后确认 | 经过现有知识校验，生成针对当前证据的新确认 |
| 对象缺失/映射不确定的说明 | 暂缓、归档本条理解 | 不允许确认；归档保留原文和依据，并从可复用说明中排除 |
| 逻辑关系 | 查看现有编辑器、重新校验、停用、暂缓 | 通过领域校验才可确认当前状态；停用影响传递给说明 |
| 被物理外键替代的关系 | 查看映射并确认已了解、暂缓 | 仅确认复核事项，不额外建立重复逻辑关系 |
| 业务域/保存视图成员缺失 | 查看引用、编辑成员/根表、暂缓、确认保留缺失引用 | 必须预览具体结果；保留缺失引用显示持续警示，不当作修复 |
| 新表/新字段且无已有理解依赖 | 标为已查看 | 仅表示结构变化已阅，不创建业务说明或“已理解”标记 |
| 不确定采集范围 | 重试采集、检查来源与范围 | 不提供“忽略并判定无影响”按钮 |

所有破坏性理解操作（归档/停用/移除视图成员）先展示本地影响，保留审计。P0 不提供一键确认全部知识。

归档属于知识生命周期变化，不是删除注释，也不是仅隐藏待办：必须统一接入检查面板、AI 上下文、搜索、导出与共享投影，默认不把归档说明作为当前说明输出。归档/恢复只在本机有效；共享可传普通文本但不携带本机确认。恢复归档须生成待复核事项，不恢复旧的确认资格。

### 4.5 完成本轮

- “已查看结构变化”与“已确认理解”是不同的计数与记录。
- 所有本轮结构变化组（按表/对象族分组）需要显式已查看；允许对用户选定的结构组批量标已查看，不能联动确认知识。
- 所有阻塞影响事项已解决或明确归档/停用；暂缓仍阻塞完成。
- 对视图明确保留缺失引用的决定可视为已处理，但结算摘要必须保留“已接受限制”，不显示全面正常。
- 完成对话框展示范围、已查看结构组、确认/修订/归档计数、已接受限制；文案为“完成本轮范围内复核”，不称“数据库验证通过”。
- 后端再次校验当前目标、来源身份、事项版本、覆盖状态和待办计数，在同一事务中完成轮次并推进基线。
- 无理解受影响但存在结构变化时，仍需用户查看结构并显式完成，不自动推进。

## 5. 状态与边界规则

### 基线与刷新

- Baseline = 用户完成复核的比较参考；Target = 当前轮次待核对的最新采集快照。
- 活动轮次中刷新：baseline 不变；target 前移并增加 revision；旧目标、旧事项版本与决定保留在日志。
- 不覆写用户正在编辑的文本。提示“发现更新，请重新检查”，保留本地草稿并拒绝旧版本提交。
- 仅当对象版本、直接与传递依据摘要、来源身份、覆盖契约均相同时，已处理决定可沿用；否则新增事项版本并重新待办。
- 某变化回退到基线状态时标记为“不再适用”，保留记录；不能据此复活已经被作废的知识确认。
- 结构未变化但用户在其他入口修改说明或关系，也需使工作区失效重算；不能只监听快照变化。
- 已完成轮次不可编辑；恢复或纠正通过新的处理记录/轮次进行。

### 采集与身份

P0 新增采集收据，至少记录采集是否成功、来源身份摘要、方言/采集器版本、请求范围摘要、已知缺口与能力覆盖。不在日志存密码或完整连接字符串。

成功连接并不证明能看见全部对象。对于可比性未知的旧快照，显示未知，不声称完整覆盖。权限缩小、范围改变或某对象突然不可见，使用“本次未观测到/范围待确认”，不要自动宣称物理删除。

已知范围不一致或采集失败不能推进基线。必要时提供显式“重新建立比较起点”：解释旧轮次终止原因，保留历史，将旧知识置待复核，不把它记录为完成旧轮次。不得把用户确认范围当作数据库权限完整性的技术证明。

来源地址/库/身份发生改变，旧基线与新来源不得直接合并。保留旧 epoch，并要求显式建立新起点。数据库凭据等非语义属性沿用现有身份规则，具体复用需单测。

### 多次采集与语义变更

同一来源多个窗口提交时，以后端 revision/CAS 为准。快照更新、知识修改与复核完成必须共享持久化版本检查；UI 按钮禁用不能替代此保护。

说明 A 依赖说明 B：B 待复核时 A 不能确认；先处理 B，再生成 A 的新依据。循环依赖继续由现有规则拒绝。事项解决后重算传递影响，不能直接给相关事项批量盖章。

## 6. 数据模型（新增设计，不是现有表）

知识有效性继续由现有 KnowledgeState 决定；复核工作流状态不替代它。业务域/视图目前没有知识确认状态，不伪造 Confirmed。

| 表 | 关键字段 | 约束与职责 |
|---|---|---|
| `review_baselines` | source_id, source_epoch, snapshot_id, kind(starting_point/reviewed), revision, established_at, last_completed_round_id | 每来源当前 epoch 一行；显式推进 |
| `capture_receipts` | id, source_id, snapshot_id(nullable), captured_at, identity_digest, scope_digest, collector_version, status, coverage_json | 失败也记录；相同结构可有新的收据；不改结构指纹语义 |
| `review_rounds` | id, source_id, source_epoch, baseline_snapshot_id, target_snapshot_id, target_receipt_id, state, revision, semantic_revision, created_at, completed_at | source+epoch 最多一个 open；state=open/completed/superseded |
| `review_items` | id, round_id, item_key, item_revision, kind, target_key_json, causes_json, before_json, after_json, evidence_digest, disposition, resolution_code, decision_id | 稳定 item_key；状态 open/deferred/resolved/not_applicable；旧版本由事件保存 |
| `review_events` | id, operation_id, round_id, item_id(nullable), event_type, expected_revision, before_json, after_json, evidence_json, created_at | 追加写；operation_id 幂等；记录处理、重开、目标变更、完成 |
| `knowledge_lifecycle` | source_id, object_key, state(active/archived), revision, archived_at, reason | 本机归档；所有当前知识消费者统一过滤 |
| `review_dirty_sources` | source_id, semantic_revision, last_processed_revision | 事务内标脏；崩溃后可重建，不因刷新返回失败丢失待办 |

`ReviewCause`：结构化 reason_code、change_operation_key、dependency_path、before/after 属性、coverage_status、severity。文案由前端国际化生成，不能依赖解析英文 reason 字符串。

`ReviewItem.kind`：structure_group / annotation / logical_relationship / domain_group / saved_view / coverage。结构组与理解影响分开展示与计数。

摘要字段仅包含相关依据的规范化数据；P0 annotation 仍使用完整依赖表摘要。item_key 使用 source_epoch、对象标识、事项类型；不得只用易变列表下标或标题。

事项是可重建的工作投影；事件、用户决定、基线与确认记录是不可丢失的数据。不要在每次重算时清空并重建用户决定。

### 历史与清理

- 保护当前基线、活动轮次目标、有效确认所需依据快照，避免现有历史保留策略裁剪。
- 完成轮次的事件保存足够的局部前后证据；若按明确保留策略裁剪完整快照，历史页提示局部证据，不假装仍能显示全图。
- 来源删除和本地重置清理所有新增表；便携备份/Git/云分享不携带本机确认资格与复核完成证明。
- 普通应用重启/升级保留轮次；便携导入后重新建立比较起点，导入说明需本机复核。
- schema migration 幂等；无基线旧库默认未初始化，不能自动生成 completed 记录。

## 7. 后端架构与接口

新增 `crates/semantic-model/src/change_review.rs`：纯函数计算影响，输入基线/目标快照、结构差异、原始语义对象、现有知识状态、收据与先前决定；输出结构化事项。避免引入网络、数据库或 AI 依赖。

新增 `crates/snapshot-store/src/change_review.rs`：表初始化、事务、事件、版本校验与轮次生命周期。现有知识/关系写操作提取 transaction-aware helper，支持“更新理解+确认+事件+事项结果”同一事务；不得串联两个各自提交的 IPC 来伪装原子性。

新增 `apps/desktop/src-tauri/src/change_review.rs`：输入校验、安全错误、页面请求调度；在 lib.rs 注册命令。

拟定接口：

| 命令 | 主要输入 | 主要输出 |
|---|---|---|
| `get_change_review` | sourceId, filter, cursor, limit | 轮次摘要、覆盖状态、分页事项、revision |
| `establish_review_start` | sourceId, expectedSnapshotId, expectedIdentity | 比较起点/初始化轮次；不确认说明 |
| `get_change_review_item` | roundId, itemId | 可读原因所需数据、前后属性、依赖路径、动作可用性 |
| `prepare_review_resolution` | roundId, itemId, expectedRevision, action, proposedText? | 本地预览、当前依据摘要、过期时间、影响预览 |
| `apply_review_resolution` | previewId, operationId, expectedRevision | 原子提交结果、最新轮次版本、受影响事项摘要 |
| `mark_structure_groups_seen` | roundId, groupIds, expectedRevision, operationId | 结构组已阅结果，不改变知识有效性 |
| `complete_change_review` | roundId, expectedRevision, operationId | 完成摘要或明确的剩余阻塞项 |

所有事务内二次检查 source epoch、最新 snapshot、semantic revision、对象版本和依据摘要。重复 operationId+相同输入返回相同结果；不同输入返回冲突。预览默认 10 分钟有效，刷新目标/证据变化立即失效。

采集集成：在现有成功采集事务中保存收据并标脏。影响计算在事务外基于一致性输入快照完成，再以 CAS 安装投影；并发变化则重算。UI 显示“正在计算影响”，此时禁止完成。保持大图采集响应，不在 SQLite 写锁内执行重计算。

单纯业务说明变更也在所有写入路径标脏（本地编辑、Git/云导入、恢复、关系操作）；沿用现有数据库 trigger 覆盖多入口的原则。失败不能推进基线；后台处理失败可重试，并保留旧轮次。

## 8. 前端落点

- 新增 `platform/change-review-types.ts` 及 desktop platform API；Web 返回明确 unsupported。

- `App.tsx` 只做工作区切换和来源绑定，具体状态放入专用 hook，按 sourceId+epoch 隔离请求与草稿。

## 9. 开发顺序与每步退出标准

| 顺序 | 工作包 | 必须完成才能进入下一步 |
|---|---|---|
| 0 | 固定合成案例、状态术语和三种界面状态草图（待处理/并发变化/完成） | 验收案例可重放，产品动作与状态无歧义 |
| 1 | 收据、基线、轮次、事件、归档迁移与快照保留 | 老库升级不丢记录、不伪造确认；重启恢复与裁剪测试通过 |
| 2 | 纯函数影响投影、结构组与保守表级原因 | 直接/传递失效、无关变更、回退和范围不明案例通过 |
| 3 | 事务提交、幂等、CAS、现有知识 helper 整合 | 并发刷新/确认、双窗口、失败回滚不产生错误完成 |
| 4 | 工作区 UI、原对象入口、前后对比和局部图导航 | 不读 JSON 可完成基本复核，长文本/空状态/失败可用 |
| 5 | 刷新提示、已有入口变更联动、完成摘要 | 活动轮次更新不丢待办，所有阻塞项可定位 |
| 6 | PostgreSQL/MySQL fixture 与原生桌面验收 | 完整闭环、数据保留、键盘/中英/缩放和性能结果记录 |

每步可分独立提交。阶段 3→4 是首个可运行端到端切片；不要先做大范围视觉改版再补状态模型。

性能目标（待测，非当前承诺）：固定测试设备记录配置；500 表、2,000 影响项的合成数据上，已缓存工作区首屏 p95 ≤1s，单项打开 p95 ≤300ms；列表交互不挂载全库图。2,000 表压力样本记录耗时、内存和主线程长任务，允许明确加载进度但不得卡死、丢操作或误判完成。不能用构建/单测通过代替原生 WKWebView 验收。

最终验收演示：订单/支付样例中预存确认说明和视图；外部修改字段可空性、删除一项引用、新增无关表；刷新看到影响；修订一条、暂缓一条；重启后继续；解决剩余项；显式完成；再次刷新确认新变化以新基线计算。

## 11. Three.js 决策

P0 不引入 Three.js。它提供 scene/camera/renderer 的图形渲染能力（[官方 Fundamentals](https://threejs.org/manual/pages/fundamentals.html)），并不直接解决知识有效性、前后属性比较或复核流程。

当前任务以文本、字段差异和依赖路径阅读为主。三维视角会新增遮挡、摄像机操作、命中测试、可访问性和导出维护工作；这些是本产品的工程判断，不是 Three.js 本身的能力缺陷，也不假设它一定更慢。

“更酷”优先通过二维信息表达实现：稳定布局上的变化高亮、点击事项直接定位、前后切换、依赖路径强调、克制的过渡和清晰的完成反馈。只播放事件触发的短动画，遵守减弱动效，不做持续旋转或粒子背景。

若未来用户研究证明空间视图能更快完成特定复杂关系任务，可独立做只读原型，与二维方案比较任务耗时、错误率、可访问性和性能，再决定是否集成。没有这类证据前，不作为架构依赖。

## 12. 开工决策与剩余核验

本方案默认：桌面、本机、一个来源一个活动轮次；暂缓阻塞完成；确认基线显式推进；不增加任何数据库写能力；不依赖 AI 和 Three.js。无需等商业定价或 App Store 接入才可实施。

阶段 0/1 必须核验各适配器目前可提供的权限/范围诊断，确定 receipt 能诚实声明的覆盖边界；不能以补一个 success 字段替代此工作。归档属于跨消费者变更，若未完成所有当前知识出口隔离，P0 不得发布归档按钮。无需等待未来字段级依赖，但界面必须清楚标识保守影响判断。
