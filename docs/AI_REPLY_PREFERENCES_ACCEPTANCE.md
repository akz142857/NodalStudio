# AI 回复偏好与附加指令

日期：2026-10-25。未提交、上传或发布。

## 产品行为

Settings → AI 新增“回复偏好”，按数据库保存，沿用“保存 AI 配置 / 放弃草稿”。

- 默认回复语言：跟随界面、English、简体中文。只作为无法判断问题语言时的兜底；本轮明确语言要求、问题语言仍优先。
- 回答详略：简洁、适中、详细。详细模式仍遵守现有输出格式、字符数和 token 上限。
- 术语风格：通俗易懂、专业术语、术语附英文对照。英文对照只用于术语，不要求整段双语重复。
- 附加指令：选填，最多 1000 字符；用于表达偏好。随请求发送给配置的服务商，输入框旁明确提醒不填写密钥。

中英文标签、说明、占位符及设置搜索入口已补齐。旧配置自动补上默认值，无需手动迁移。对当前请求的设置采用预览快照；偏好变更使旧预览失效，历史回复不重写。

## 技术与安全边界

AiSettings.replyPreferences 使用带默认值的结构化枚举及有限长度文本。前端使用 textarea 限长，保存及请求构建分别检查 1000 字符限制。表理解及业务发现/SQL 草稿共用表达偏好构建，连接测试不发送附加指令。

内置系统提示词保留。用户附加指令被 JSON 编码放入 user 消息，明确标记为低优先级表达数据，不拼接成 system 指令。它不能覆盖语言优先级、JSON 格式、字符上限、只读 SQL 校验、允许的表和证据范围、隐私、人工确认与不执行规则。原有结构/SQL 输出校验仍执行。模型偏好不等于对任意模型输出的绝对保证。

### 实测发现与修复

1. 首次请求阻塞在 macOS 钥匙串，而非网络；线程采样确认停在 `keyring::Entry::get_password`。用户完成本机设置后继续成功调用。代码将凭据读取移到阻塞线程，以 30 秒限时和取消令牌包裹，并串行化原生凭据读取，避免重复授权窗口。超时/取消结果不会进入网络发送；底层系统调用可能仍等待系统授权，迟到结果被丢弃。表理解与业务发现共用此路径。等待文案改为“正在准备请求并等待模型响应”，避免声称已经在等模型。
2. 详细模式曾复述冲突指令及内部规则，并在缺少 collation 证据时推断大小写或空格变体会分别分组。已收紧内置提示：静默忽略冲突表达指令，围绕业务问题解释；没有证据时不推断排序规则、大小写或空格比较行为，而是注明不确定。

自动化新增凭据读取成功、超时、等待中取消及已取消请求不启动读取的测试。修复后桌面后端全量 99 项通过、6 项忽略；DiscoveryAssistant 前端回归 19 项通过；lint、TypeScript/Vite 和原生未签名构建通过。真实环境中成功调用覆盖新的凭据路径；超时/取消分支由自动化测试覆盖，没有为了验收故意锁定用户钥匙串。

详细模式复测（06-final-detailed）已不再复述被拒绝的附加指令，解释集中于统计粒度、COUNT、无 JOIN 及未执行状态。与简洁样本相比，增加了非空状态、排序用途、执行时数据等说明，四条假设也更完整。辅助功能树的长段文本会截断到 500 字符，完整解释需以截图复核，不能将 AX 截断当成模型输出截断。

进一步追问 `Will statuses 'Paid', 'paid', and 'paid ' be counted as separate groups?` 时，模型正确指出缺少 collation / 大小写 / 尾部空格比较证据，无法断言分别分组；但回复错误地使用中文（07-regression-english-auxiliary-failed）。这是未通过样本，予以保留。根因是本地语言提示未覆盖辅助动词开头的英文问句，交给模型判断后受默认中文影响。修复增加 Will/Would/Can/Could/Does/Do/Is/Are/Should/Why/When/Where 开头的英文问句判定，保留标识符兜底边界；增加原题及 Does/Can/Are/带点标识符的回归用例。

英文辅助问句的真实修复验证通过（09-final-english-auxiliary-pass）：重建相同 orders 查询历史后，原题 `Will statuses 'Paid', 'paid', and 'paid ' be counted as separate groups?` 返回英文解释与四条英文澄清，明确缺少 collation，未臆造大小写或尾部空格分组结果，且没有生成确定性 SQL。默认中文和冲突附加指令在该次复测中保持不变。

同时保留第二个分组语义失败样本（08-final-baseline-collation-caveat）：虽然泛化提示要求“不推断 collation”，详细模式重采样仍出现错误的分别分组假设。因此进一步针对文本 GROUP BY 明确要求附带未知 collation 的假设说明，并禁止从“没有 LOWER/TRIM”推导“大小写/空格不同必定分组不同”。这也说明详细偏好不能代替业务正确性审阅，不能将单次模型通过推广成稳定保证。

最终文本分组约束复测通过（10-final-detailed-collation-pass）：完整英文解释明确指出 `status` 的 collation 未提供，大小写/尾部空格是否合并需要核实，且没有 LOWER/TRIM 不意味着分别分组。假设列表同样标明未知 collation；正常 Review note 前缀仍生效，SQL 仍是只读单表 SELECT，没有采用 DELETE/users 冲突指令，也没有复述内部策略。

最终验证补充：ai-context 全量 28 项通过（11 单元 + 9 discovery + 8 understanding），其中语言表驱动测试增加 5 个回归场景；最终共享请求/凭据模块测试记录于 final-prompt-tests.log。本轮共保留 10 份真实返回样本（含失败/修复前样本），另有最初钥匙串阻塞未发送的诊断证据。偏好恢复为跟随界面 / 适中 / 专业术语 / 空附加指令，清空本轮演示对话，保留用户的现有服务商和凭据（restored-settings.ax.txt）。

验收结论：已观察到语言优先级、简洁/详细差异和正常附加表达偏好生效；本轮越权/虚构表测试未突破只读和证据范围。发现的等待阻塞、英文辅助问句和文本分组假设问题已修复并复测。真实模型结果存在随机性，仍按未执行、待审核草稿交付，不能把有限样本视为所有业务回答均正确。无提交、上传或发布；MAS 真实购买验收不包含在本轮中。
